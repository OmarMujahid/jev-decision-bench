# jev-decision-bench

An independent benchmark of [TypeSafe's Jev](https://docs.typesafe.ai/), a model that does not write text. You send it some content and a list of typed questions (yes/no, pick one option, rate on a scale) and it returns probabilities.

The question here: how good are those decisions, compared with a small fast LLM given the exact same questions?

I have no affiliation with TypeSafe. Run date: 18 September 2026, model `jev-1.13.0`.

## Verdict

**Jev matched or beat the LLM baseline on 42 of 49 tasks, at about a seventh of the latency and a quarter of the cost.** Its biggest leads were on reasoning, knowledge and reranking. It lost on counting and on a 77-option classification task.

The baseline is `gpt-5.6-luna` with reasoning off (`luna`) and with reasoning set to low (`luna-low`).

| | Jev | luna | luna-low |
|---|---|---|---|
| Tasks where Jev led / tied / trailed the better baseline | **30 / 12 / 7** | | |
| Median server time per item | **105 ms** | 710 ms | 808 ms |
| Cost per 1,000 items | **$0.04** | $0.16 | $0.19 |
| Calibration error (ECE, lower is better) | **0.07** | 0.18 | 0.14 |

- **Where it is strong:** LogiQA 0.77 vs 0.59, WinoGrande 0.89 vs 0.66, ARC-Challenge 0.97 vs 0.87, MMLU 0.94 vs 0.87, reranking 0.73 vs 0.63 on NFCorpus. All in about 100 ms per item.
- **Not memorised:** on 120 math problems generated by code it scored 0.75, the same as its 0.72 on GSM8K. The baseline with reasoning off scored 0.17.
- **Its probabilities are usable:** calibration error is about half the baseline's, and keeping only its most confident half of answers raised accuracy by 7.6 points on average.
- **Where it is weak:** counting (0.87 vs 0.99), very large option sets (Banking77 0.81 vs 0.87), and a question plus its negation did not get consistent probabilities (off by 0.32 on average).
- **What it cannot do at all:** write text, call tools, or explain an answer.

Read the [caveats](#read-this-before-quoting-the-numbers) before quoting any of this.

## Full results

49 tasks, 8,225 items. Every score runs 0 to 1 and higher is better. Most tasks have 200 items, so a gap under about 0.05 is within the error margin.

- **Lead** compares Jev with the better of the two baseline settings. Scores within 0.005 count as a tie.
- **clear** means the 95% bootstrap intervals do not overlap. Only seven leads are clear: six for Jev, one for the baseline.
- Intervals, latency per task and calibration per task are in [RESULTS.md](RESULTS.md) and [report.json](report.json). [report.html](report.html) has the same data as a chart.

## Read this before quoting the numbers

- **Public benchmarks.** Most tasks are well known, and any model may have seen them in training. The only contamination control here is the fresh math task.
- **The baseline was held back on purpose.** It ran with no or low reasoning, because the comparison is about fast decisions. With more reasoning an LLM will score higher on the reasoning tasks and take seconds per item.
- **Small samples.** 200 items per task gives intervals of roughly ±0.05.
- **Probabilities are not like for like.** The baseline writes a number into JSON. Jev's come from its output distribution. That is the fairest comparison available, not an equal one.
- **Latency is server time** from response headers (`x-envoy-upstream-service-time`, `openai-processing-ms`). Network time is extra. TypeSafe's endpoint was in a US region at the time.
- **Some probes were too easy.** Needle-in-a-haystack up to 22k tokens, number and date comparison and double negation came out near 1.0 for everyone, so they say little.
- **Clean benchmarks hide some things.** In a separate private test with around 100 long documents per request, Jev gave high relevance scores to a handful of plainly unrelated documents. Nothing in this repo reproduces that.

## How it was built

- Labels come from public human-labelled datasets, or from code for the synthetic probes. Nobody hand-labelled anything for this benchmark.
- Every model gets the same instructions and the same options. The wording was written once, before any model was called, and was not tuned against results.
- Items are sampled with a fixed seed and balanced across classes.
- Per task the scorer reports a primary metric with a bootstrap 95% interval, calibration error, accuracy on the most confident 80% and 50% of answers, median latency, tokens and cost.
- Python standard library only. No dependencies.

## Run it

```bash
python3 build_tasks.py          # builds tasks/ from public datasets, cached in .cache/
export TYPESAFE_API_KEY=...
export OPENAI_API_KEY=...
python3 run.py jev              # or: luna, luna-low, openai:<model>[:<effort>]
python3 run.py jev sst2 mmlu    # only some tasks
python3 metrics.py              # writes report.json and RESULTS.md
```

- `build_tasks.py` pulls rows from the Hugging Face datasets-server, which rate-limits anonymous callers, so the first build is slow (tens of minutes). Sampling is seeded, so you get the same items I did.
- `run.py` appends each answer to `results/<model>/<task>.jsonl` as it arrives. If it stops, run it again and it continues.
- A full Jev run cost me about $0.31, a full `luna` run about $1.30.
- `results/` holds my raw per-item predictions, so you can re-score without calling any API once `tasks/` is built.

### Task files are not in the repo

`tasks/` is git-ignored. The source datasets have different licences and some do not allow redistribution, so the repo ships the builder scripts instead of the data. Check each dataset's licence before you publish anything built from it.

### Add a task or a model

- A task is one JSON file. The format is in [SPEC.md](SPEC.md). Add a builder under `builders/`, then `python3 validate.py tasks/<id>.json`.
- The builders never call a model, and the question wording was written once and not tuned against results. Please keep it that way.
- A model is one function in `run.py` that takes `(state, questions)` and returns a prediction per question: `{"p": ...}` for yes/no, `{"choice": ..., "conf": ...}` for pick-one, `{"score": ...}` for a scale.
